## Overview

In this tutorial you'll draw the **schematic** of a minimal ESP32 WiFi test
board — the kind of board you build when you want to verify that a module,
antenna, and power supply all work before designing a full product around
them. This mirrors the flow used in hardware design courses: bring up power,
bring up USB, bring up the module.

Every part in this design is either a **JLCPCB basic part** (no extra fee at
assembly) or a widely stocked JLCPCB part, so the schematic can go straight
to fabrication without hunting for alternates.

## Block Diagram

The board follows the classic ESP32 dev-board architecture:

```
USB-C ──► AMS1117-3.3 ──► 3.3V rail ──► ESP32-WROOM-32E
  │              │                        ▲    ▲
  │              └── Power LED            │    │
  ▼                                       │    │
CP2102N ◄──── USB D+/D- ──►  USB         │    │
  │  │                                   │    │
  │  └── UART (crossed TX/RX) ───────────┘    │
  │                                           │
  └── DTR/RTS ──► auto-program (Q1/Q2) ───────┘
```

## Power Supply: AMS1117-3.3

The **AMS1117-3.3** is the workhorse LDO of cheap dev boards — it's a JLCPCB
**basic part**, meaning it costs nothing extra at assembly. USB-C VBUS (5V)
goes in, a clean 3.3V rail comes out.

Three capacitors surround it:

- **C1 (10µF)** — input bulk capacitance on VBUS
- **C2 (22µF)** — output bulk capacitance; AMS1117 needs a real load
  capacitor on its output to stay stable
- **C3 (100nF)** — high-frequency decoupling close to the regulator

A red **power LED (LED2)** with a 1k series resistor (R6) hangs off the 3.3V
rail so you can see at a glance that power is alive.

## USB-UART Bridge: CP2102N

The **CP2102N-A02-GQFN24R** converts USB to UART so your computer can talk
to the ESP32 and program it. Only the pins that matter for this board are
modeled:

- `D+` / `D-` — straight to the USB-C connector data lines
- `TXD` / `RXD` — the UART data lines
- `DTR` / `RTS` — handshaking lines, used by the auto-program circuit below
- `REGIN` — internal regulator input, tied to VBUS
- `VDD` — 3.3V supply, with a 100nF decoupling capacitor (C4)

:::note

UART is **crossed**: the bridge's TXD feeds the ESP32's RXD0, and the
bridge's RXD listens to the ESP32's TXD0. Mixing these up is the #1 cause of
"my dev board doesn't boot" schematics.

:::

## Auto-Program Circuit: The Cross-Coupled Transistor Pair

This is the cleverest part of any ESP32 board. To put the chip into the
bootloader, `IO0` must be low while `EN` rises. But the USB-UART driver only
gives you two extra lines — `DTR` and `RTS` — and they **both** assert when
a serial port opens.

The fix is the classic cross-coupled NPN pair (Q1, Q2, SS8050):

- `RTS` → R1 → Q1 base; Q1 collector drives **EN**
- `DTR` → R2 → Q2 base; Q2 collector drives **IO0**
- Each base is biased by the *other* transistor's collector, so only one
  transistor conducts at a time

This creates an XOR-like behavior: when the driver toggles DTR/RTS in
opposite directions, exactly one of (EN, IO0) is pulled low — producing the
EN-falling + IO0-low edge the bootloader needs. Programming tools like
`esptool.py` toggle these lines automatically, so flashing works with zero
buttons pressed.

## ESP32-WROOM-32E Module

The ESP32-WROOM-32E is a certified module with the RF front-end already
designed — the reason we use it for a *test* board. The schematic models the
pins that matter:

| Pin | Function | Support circuit |
|-----|----------|-----------------|
| `3V3` | Power | 100nF decoupling (C6) |
| `EN` | Active-high reset | 10k pull-up (R3) + 1µF delay cap (C5) |
| `IO0` | Boot strap | 10k pull-up (R4) + BOOT button (SW1) |
| `IO2` | User GPIO + strap | Green LED via 1k (R5, LED1) |
| `TXD0`/`RXD0` | UART0 | Crossed to CP2102N |

Two strapping details that matter:

- **EN needs a slow rise.** The 1µF capacitor (C5) on EN gives the chip a
  power-on-reset delay — without it, a fast-railing supply can leave the
  chip in a half-configured state.
- **IO0 must be high** for normal flash boot, and low for the serial
  bootloader. The 10k pull-up handles the normal case; pressing SW1 during
  reset forces the bootloader.

:::tip

IO2 is also a strapping pin — it must be low or floating during boot. A
green LED with a 1k resistor is weak enough that it doesn't disturb the
strap, while doubling as your "firmware is alive" blinker.

:::

## Bringing It Together

Every connection in the schematic is a `<trace>` element referencing pins by
their labels — for example `<trace from=".U2 > .pin6" to=".U3 > .pin7" />`
crosses the UART lines. Because the labels were declared once on each chip's
`pinLabels`, the netlist stays readable: `pin6` of the bridge *is* `TXD` by
definition.

## Verifying the Design

You can check this board compiles to a valid netlist by building it with the
tscircuit CLI:

```bash
tsci build esp32-wifi-test-board.circuit.tsx
```

A successful build means every trace lands on a real port and the netlist is
electrically consistent — the schematic equivalent of "it compiles".
